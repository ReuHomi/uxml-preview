# devlog

이번 세션을 `docs/progress.md`에 기록한다.

**기록처는 여기 하나뿐이다.** 별도의 devlog 문서를 만들지 않는다. 기록처가 둘이면
둘 다 썩는다. `docs/progress.md`의 세션 로그 절이 그 역할을 이미 하고 있다.

## 대상 파일 (고정)

파일을 탐색하지 않는다. 아래가 전부다.

| 파일 | 언제 |
|---|---|
| `docs/progress.md` | **항상.** 대부분의 갱신이 여기서 끝난다 |
| `docs/architecture.md` | 3절의 트리거에 걸릴 때만 |
| `docs/ROADMAP.md` | Phase DoD 체크박스 상태가 바뀌었을 때만 |
| `docs/backlog.md` | v0.1 스코프 밖으로 민 항목이 생겼을 때만 |

## 0. 날짜 확정 (반드시 첫 단계)

```bash
date "+%Y-%m-%d %H:%M"
```

**추측하지 않는다.** 자정 기준 24시이고 보정하지 않는다 — 00:30에 실행하면 그 날짜다.
여기서 얻은 날짜를 헤더에, 시각을 같은 날 재기록 표기에 쓴다.

## 1. 무엇이 있었는지 확인

정보원 우선순위:

1. **이 세션에서 실제로 한 작업** — 대화에 남아 있는 것
2. `git log --oneline`, `git diff --stat`, `git status --short`
3. 사용자에게 묻는다

**확인되지 않은 것은 쓰지 않는다.** 하지 않은 구현을 그럴듯하게 지어내는 것이
이 스킬의 최악의 실패다. "아마 했을 것"은 쓰지 않고, 애매하면 묻는다.

테스트를 돌렸다고 쓰려면 실제로 돌린 결과가 있어야 한다. 실패한 것은 실패했다고 쓴다.

## 2. progress.md 갱신

파일은 네 절로 되어 있고 이 순서를 유지한다.

| 절 | 방식 |
|---|---|
| 현재 위치 | 덮어쓴다 |
| 다음 할 일 | 덮어쓴다 |
| 결정 기록 | append — 표에 행 추가 |
| 세션 로그 | append — **최신이 위** |

**append-only.** 결정 기록과 세션 로그의 기존 문장은 수정·삭제하지 않는다.
결정이 뒤집히면 지우지 말고 새 행으로 뒤집는다. "왜 그때 그렇게 판단했나"가
남아야 같은 실수를 반복하지 않는다.

> 이 스킬은 `Write` 도구를 쓸 수 없다(`allowed-tools`에서 제외). `Edit`만 가능하므로
> 파일을 통째로 덮어쓰는 사고가 구조적으로 불가능하다.

### 같은 날짜에 다시 기록할 때

`### YYYY-MM-DD` 헤더가 이미 있으면 **새 헤더를 만들지 않는다.** 기존 항목에
이어 붙이고, 이어 붙인 첫 줄에 `(HH:MM 추가)`를 표기한다.
하루에 몇 번 끊겼는지가 그 자체로 기록 가치가 있다.

### 세션 로그 항목

절 제목을 강제하지 않는다. 아래 중 해당하는 것만 쓴다.

```markdown
### YYYY-MM-DD
- 한 일 — 파일·함수 단위로 구체적으로
- 발견한 것 / 막힌 것 — 인지 → 정체 → 해결 순으로. 실패한 접근도 남긴다
- 다음에 바꿀 것 — 지금은 이렇게 했지만 개선 여지가 있는 부분
```

### 결정 기록에 올릴 것

"나중에 왜 그랬는지 물을 만한 것"만 올린다. **이유 칸이 핵심이고, 결정 자체는
이유의 요약일 뿐이다.** 6개월 뒤에 실제 판단 근거가 될 것만 쓴다.

나쁜 예 — 자기 만족적이고 정보가 없다:

> | 2026-08-02 | 파서를 모듈로 분리 | 유지보수성과 확장성 향상 |

좋은 예 — 조건과 트레이드오프가 있다:

> | 2026-08-02 | 왕복 기준을 "git diff 청결"로 | 바이트 일치는 XML 선언·따옴표 종류까지 보존해야 해서 모델이 비대해진다. 사람이 열었다 저장했을 때 diff가 안 나오면 실무에선 충분하다. 픽스처에서 diff가 실제로 새면 그때 바이트 일치로 올린다 |

## 3. architecture.md — 걸릴 때만

**갱신 대상 절만 수정한다. 나머지는 그대로 둔다.**

| 갱신 대상 | 트리거 |
|---|---|
| 데이터 흐름 | 계층이 늘거나 순서가 바뀜 |
| 핵심 설계 결정 | 새 결정이 구조에 영향을 줌 |
| 디렉토리 | `src/` 하위 디렉토리 추가·삭제 |
| 소유권 / 생명주기 | Yoga 노드나 DOM을 누가 만들고 누가 해제하는지가 바뀜 |

**타입과 시그니처를 문서에 복사하지 않는다.** SSOT는 `src/index.ts`와
`src/model/types.ts`이고, 문서는 그 파일을 가리키기만 한다. 복사본은 조용히
어긋나고, 어긋난 문서는 없는 문서보다 나쁘다.

트리거에 걸리는지 애매하면 **갱신하지 않는 쪽**을 택한다.

## 4. 상태 표현

아래 다섯 개 외의 표현을 쓰지 않는다.

- `미구현` — 아직 시작 안 함
- `구현 중` — 진행 중
- `코드 작성` — 코드는 있고 테스트로 검증되지 않음
- `검증됨` — 왕복 테스트 또는 골든 테스트 통과
- `보류` — 의도적으로 미룸. `docs/backlog.md`에 이유와 함께 적는다

**`코드 작성`과 `검증됨`을 뭉개지 않는다.** 이 프로젝트에 Phase 5가 따로 있는
이유가 그것이다. "유니티랑 똑같이 나오냐"에 숫자로 답하지 못하면 검증된 게 아니다.

## 5. 문체

- **이모지를 쓰지 않는다.** (`README.md` 상태표의 기존 표기는 예외 — 건드리지 않는다)
- 문어체. 구어체·존댓말·인사말·사과를 쓰지 않는다
- 강조는 `**볼드**`, 구분은 `---`, 상태는 표
- 코드 블록은 핵심 패턴만. 파일에 이미 있는 코드를 옮겨 적지 않는다

## 6. 마감 확인

1. `date`를 실행했고, 헤더 날짜가 그 출력과 일치하는가
2. 확인되지 않은 내용을 쓰지 않았는가
3. 기존 세션 로그·결정 기록을 건드리지 않았는가 — 추가만 했는가
4. 갱신한 곳을 한 줄씩 보고한다 (어느 파일, 어느 절)
