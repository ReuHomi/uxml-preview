# Architecture

## 데이터 흐름

```
        UXML 텍스트        USS 텍스트
             │                 │
             ▼                 ▼
      ┌──────────────────────────────┐
      │  L1. 스캐너 (직접 작성)      │
      │  위치를 기록하며 훑는다      │
      └──────────────────────────────┘
                    │
                    ▼
      ┌──────────────────────────────┐
      │  [ 데이터 모델 ]             │  ← 편집은 전부 여기에 가해짐
      │  VisualElementNode 트리      │

      │  + USS 규칙 목록             │
      │  + 원본 서식 정보            │
      └──────────────────────────────┘
             │                 │
             ▼                 ▼
   ┌──────────────┐   ┌──────────────────┐
   │ L2 스타일     │   │  직렬화          │

             ▼

```

## 핵심 설계 결정

### 1. 레이아웃은 Yoga에 위임

Unity UI Toolkit은 Flexbox의 부분집합을 구현한 Yoga를 레이아웃 엔진으로 사용한다.
직접 구현하면 미묘한 차이가 누적되어 반드시 어긋난다.

`yoga-layout` npm 패키지가 공식 WebAssembly 빌드를 제공하므로 그대로 쓴다.

**주의**
- **`yoga-layout` 기본 엔트리는 top-level await을 쓴다.** import하는 것만으로
  이 라이브러리의 모듈 그래프 전체가 비동기가 되고 `render`를 동기로 유지할 수 없다.
  그래서 항상 `yoga-layout/load`를 경유하고, 호스트가 `await loadLayoutEngine()`을
  한 번 호출한다
- **Yoga 기본값은 USS와 부분적으로만 같다.** `flex-direction`(column)과
  `box-sizing`(border-box)은 일치하지만 `flex-shrink`는 Yoga 0 / USS 1이다.
  지원 속성은 전부 명시적으로 설정하고, 어느 게 우연히 맞았는지 따지지 않는다
- **enum 값을 숫자로 적지 않는다.** `PositionType.Absolute`는 2이고 0은 `Static`이다.
  틀려도 타입 검사와 테스트를 통과하는 종류의 오류다
- Yoga 노드는 자동 GC되지 않는다. `freeRecursive()` 호출 필수.
  JS 바인딩에 `getInstanceCount`가 없으므로 생성 수를 직접 센다 (`liveNodeCount()`)
- **레이아웃과 페인팅 사이가 누수 구간이다.** 노드는 `layoutDocument`에서
  할당되는데 `dispose`는 그 뒤에 만들어지는 `RenderResult`에만 달려 있어서,
  중간에 예외가 나면 트리가 영영 안 풀린다. `render`가 `paint`를 `try/catch`로
  감싸는 이유다. 놀이터는 키 입력마다 이 경로를 타므로 한 번 새면 계속 샌다

### 2. 캔버스가 아니라 DOM으로 그린다

Yoga가 계산한 좌표에 `position: absolute` div를 배치하고, 시각 속성만 CSS로 변환한다.

**이유**
- 텍스트 렌더링·폰트·안티앨리어싱을 브라우저에 맡길 수 있다
- 클릭 판정, 스크롤, 접근성이 따라온다
- 편집 레이어에서 DOM 이벤트를 그대로 쓸 수 있다

**주의**
- 모든 요소에 `box-sizing: border-box` (USS는 항상 border-box 동작)
- `z-index`를 출력하지 않는다 (USS에 없음, 형제 순서로 결정)

**DOM은 트리 모양으로 중첩한다. 평탄화하지 않는다.**
중첩하면 문서 순서가 곧 페인팅 순서라 "뒤 형제가 위"가 저절로 맞고,
`overflow: hidden`이 자손을 클리핑한다. 평탄한 목록으로 그리면 둘 다 직접
구현해야 하고, 그 구현이 곧 z-index를 다시 들여오는 길이 된다.
**좌표 변환에 함정이 하나 있다.** Yoga가 주는 좌표는 부모 기준이라 패널 좌표로
누적해뒀다가 페인팅에서 다시 빼는데, **그때 부모의 border 폭도 같이 빼야 한다.**
Yoga는 부모의 **border box 원점** 기준으로 자식 위치를 주지만, CSS에서
`position: absolute` 자식의 containing block은 **padding box**(border 안쪽)이기
때문이다. 안 빼면 브라우저가 border 폭을 한 번 더 더한다.

이 오류는 골든 테스트로는 잡히지 않는다. 골든은 Yoga 좌표를 유니티와 비교하는데
그 좌표는 맞고, 틀린 것은 다음 층이기 때문이다. 그래서 두 층이 서로 맞는지 보는
불변식 검사를 따로 둔다 — `tests/render/border-offset.test.ts`가 페인팅된 트리에서
패널 좌표를 CSS로 역산해 Yoga 값과 대조한다. **Yoga → DOM 변환을 건드리면
이 검사가 유일한 안전망이다.**

각 요소에 `data-uxml-node`로 `NodeId`를 붙인다. Phase 8이 클릭을 노드로 되짚는 데
쓰고, 나중에 붙이려면 페인팅을 다시 짜야 한다.

**텍스트 측정은 주입 가능하다** (`RenderOptions.measureText`).
기본 구현은 캔버스를 쓰는데 플랫폼과 설치 폰트에 따라 결과가 달라진다.
Phase 5 골든 테스트는 반드시 자기 구현을 넣어 고정해야 한다.

### 3. 계산된 값에는 출처가 따라붙고, 계산 결과는 모델 밖에 둔다

출처가 필요한 이유는 편집 기능(Phase 8)이다. 사용자가 화면에서 색을 바꿨을 때
인라인 스타일에 쓸지, 어느 USS 규칙을 고칠지를 출처 정보로 판단한다.
표현은 `StyleOrigin` — `src/model/types.ts` 참조.

**단 계산 결과 자체는 모델에 저장하지 않는다.** 저장하면 USS를 한 줄 고쳤을 때
무엇이 낡았는지 추적해야 하고, 그 추적을 한 번이라도 틀리면 사용자에게 틀린 값을
보여준다. 낡을 수 있는 데이터를 아예 만들지 않는 쪽이 안전하다.

후보 목록("어느 규칙들이 경쟁했나")도 저장하지 않는다. 화면을 그릴 때 쓰는 계산기를
해당 요소에 다시 돌려서 얻는다. 승자를 정하는 로직이 하나뿐이라 두 답이 어긋날 수 없다.

이 절은 모델 전체를 관통하는 원칙의 한 사례다 —
**모델에는 파일에서 온 것만 넣고, 계산해서 알 수 있는 것은 넣지 않는다.**
줄 번호, 펼친 shorthand, "이 컨트롤을 지원하는가"가 전부 같은 이유로 모델 밖이다.

### 3-b. 파서를 직접 쓴다 (`DOMParser`를 쓰지 않는다)

`DOMParser`는 소스 위치를 주지 않는다. 표준 DOM에 그런 API가 없다.
스팬 재출력은 요소마다 여는 태그·안쪽·닫는 태그의 오프셋을 요구하므로
DOMParser로는 성립하지 않는다.

대신 우리 스캐너는 **해석하지 않고 위치만 찾으면 된다.** 속성 값은 엔티티를
디코딩하지 않고 날것으로 두고, USS 선언 값도 문자열 그대로 둔다. 일반 XML/CSS
파서보다 훨씬 좁은 문제다.

### 4. 왕복 보존

`serialize(parse(x))`가 `x`와 같아야 한다.
주석, 속성 순서, 들여쓰기가 유실되면 실무에서 못 쓴다.

기준: **사람이 열었다 저장했을 때 git diff가 깨끗한가.**

### 5. 에셋 경로 리졸버

`background-image`가 `url("project://database/Assets/...")` 또는 `resource("...")`
형식이라 브라우저가 로드할 수 없다.

```ts
render(doc, el, {
  resolveAsset: (path: string) => string | null
});
```

라이브러리 사용자가 자기 환경에 맞게 구현한다.
리졸브 실패 시 플레이스홀더를 그리고 경고 목록에 담는다.

`@import`도 같은 이유로 같은 모양의 훅을 쓴다 — `parse(uxml, uss, { resolveImport })`.
경로가 `project://database/...` 형식이라 호스트만 파일 내용을 안다.
훅이 없거나 `null`을 반환하면 그 시트의 규칙은 참여하지 않고 경고가 남는다.

## 디렉토리

```
src/
├── index.ts          공개 API
├── model/            데이터 모델 정의
├── parser/           UXML·USS → 모델
├── serializer/       모델 → UXML·USS
├── style/            셀렉터 매칭·우선순위·캐스케이드
├── layout/           Yoga 브리지·텍스트 측정
├── render/           DOM 페인팅·CSS 매핑
└── controls/         컨트롤 타입 정의
```
