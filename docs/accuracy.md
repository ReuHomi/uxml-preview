기본 세트의 공개 수치는 **662 / 676 (169 elements, 0.7.0 에디터 테마 값 반영)**으로
그대로 유지한다.

| 항목 | 템플릿 전개 세트 | 뜻 |
|---|---:|---|
| 좌표 대조 결과 | **215 / 220** (0.6.0 전: 200 / 220) | 55 elements × `x`/`y`/`width`/`height` |
| 렌더된 케이스 | **11** | G3-1~G3-10, G3-12 |

G3-11은 Unity `CloneTree`가 순환 템플릿에서 `StackOverflowException`을 내므로
레이아웃 baseline이 없다. 코어는 같은 입력을 **fail-closed**로 차단하고
`template-cycle` 진단을 남긴다. 이 행은 위 11개 렌더 케이스나 기본 컨트롤 수치에
포함하지 않는다.

### 템플릿 전개 불일치 5건 — (a) / (b) / (c) 분류

`problems`와 `lines`는 외부 재관찰 표에서 쓰는 단위이며, 아래 골든 표는 렌더된
템플릿 케이스의 좌표 불일치만 센다. 두 숫자나 빈 상자의 일치를 정확도에 합산하지
않는다.

| 단위 | 정의 |
|---|---|
| `problems` | 코어 실패가 발생한 횟수 |
| `lines` | 코어·호스트가 진단 패널에 출력한 줄 수 |

| Case | Element | Axis | ours | Unity | Δ |
|---|---|---|---:|---:|---:|
| `G3-4` | `g34-instance` | width | 143 | 145 | -2 |
| `G3-4` | `g34-template-root` | width | 143 | 145 | -2 |
| `G3-4` | `g34-internal-label` | width | 143 | 145 | -2 |
| `G3-4` | `g34-outside-label` | x | 143 | 145 | -2 |
| `G3-4` | `g34-outside-label` | width | 153 | 140 | 13 |

분류 결과는 **(a) 5 / (b) 0 / (c) 0**이며 축 분포는 `width` 4, `x` 1이다.
0.6.0에서 하네스의 글자 높이가 `height = fontSize`에서 FaceInfo 공식
(`textHeight`, D3)으로 바뀌면서 Label 높이 14건과 그 높이에 밀린 `y` 1건이
사라졌다(200/220 → 215/220). 남은 5건은 G3-4 Label 폭이며 하네스의 고정 폭
측정(반 em)에서 오는 텍스트 메트릭 차이다.

허용 오차 0.5px. **기준 2가 허용하는 1px보다 일부러 엄격하게 둔다** — 느슨하게 하면
다른 케이스의 진짜 1px 오차가 숨는다.

### 불일치 14건의 성격 — 이 구분이 숫자보다 중요하다

| 분류 | 값 | 이것이 뜻하는 것 |

ActionBar가 경계를 나누는데, 그 경계를 라벨의 min-content 폭이 민다. **양쪽 엔진 다**
ActionBar를 압축한다 — 유니티는 93으로, 우리는 84로. 라벨 폭을 고정하면 우리 초과분이
**유니티와 똑같은 3px로 수렴한다.** 메커니즘은 같고 자만 다르다. 브라우저는 유니티
폰트 에셋을 잴 수 없고, 그건 픽셀 diff를 포기한 것과 **같은 사실이 색 대신 좌표로**
나타난 것이다.

> 이전 수치는 242/244(99.2%)였다. **비율이 내려간 것은 정확도가 나빠져서가 아니라
> 케이스가 넓어져서다** — 그때는 18케이스 중 17개가 `VisualElement`뿐이었고 `Button`은
> 한 번도 대조된 적이 없었다. 지금은 텍스트투성이 실무 화면이 들어 있고, 불일치의
> 9/14가 폰트다(처음에는 10으로 셌으나 `ItemDesc.height`는 테마 값이었고, 0.7.0에서 테마의 Label `flex-shrink: 0`으로 `ItemDesc` 2값이 맞았다). **숫자를 비교할 때는 케이스 구성을 같이 옮겨야 한다.**

> 여섯 번의 재측정에서 기존 케이스는 매번 **바이트 단위로** 재현됐다(케이스 수 20, 26, 27, 30, 32,
> 34 시점). 덤프 도구가 결정적이라서, 새 숫자를 환경이 아니라 변경 탓으로 돌릴 수 있다.

### 2026-08-12 `inventory` 1px 재현 — 기준값 유지

2026-08-12 덤프에서 `inventory`의 `DetailPanel` 폭과 `ActionBar` 폭은 각각
292px/92px로 나왔고, 같은 Editor 세션의 재덤프에서도 같은 값이 재현됐다. 기존
기준값은 291px/93px이며 현재 렌더러도 그 기존 기준값과 일치한다.

Unity 버전·리비전, OS, GPU가 같은 환경에서 같은 세션의 두 덤프는 37개 JSON 모두
바이트 단위로 같았다. 따라서 덤프 자체는 그 세션 안에서 결정적이었지만, 과거 덤프는
DPI 배율과 폰트 설정을 기록하지 않아 어느 측정 조건이 1px 변동을 촉발했는지는 확정할
수 없다. 이 조사 뒤 `UxmlLayoutDump.cs`가 Unity 버전·리비전, 에디터 DPI 배율,
접근 가능한 폰트 설정과 덤프 시각을 좌표와 분리된 메타데이터로 기록하도록 바꿨다.

이 1px은 새 기준값으로 채택하지 않았다. 허용 범위 안의 1px이고 렌더러 변경이 아니라
측정 조건 문제인데, 과거 조건을 모르는 채 기준을 옮기면 무엇에 맞추는지 알 수 없게
되기 때문이다.

### `ScrollView` — 계층을 관측해서 맞췄다 (2026-08-05)

`ScrollView`는 태그 하나가 요소 넷이 된다. 유니티가 만드는 **암묵 계층 3층**이
그 안의 모든 자식 위치를 정하므로, 박스 하나로 그리면 좌표가 어긋난다.

```
ScrollView
└── #unity-content-and-vertical-scroll-container
    └── #unity-content-viewport                  ← 클리핑
        └── #unity-content-container             ← 사용자 자식
```

**중간 층은 어느 문서에도 없었다.** 소스를 읽지 않고 덤프로 관측해서 찾았다.
덤퍼가 `hierarchy`(물리 트리)를 순회하고 유니티가 이 파트들에 이름을 주기 때문에
결과에 그냥 나온다.

측정된 규칙 셋:

- 1층은 ScrollView의 **content box**를 채운다 (padding·border 안쪽)
- 뷰포트는 **넘칠 때만** 세로 스크롤바에 13px를 내준다. 안 넘치면 스크롤바가
  `0×0`이라 폭이 온전하다 — 조건부라는 것이 값 자체만큼 중요하다
- 컨테이너 높이는 **콘텐츠 높이**다. 뷰포트에 맞춰 줄지 않는다

마지막 것이 실질이다. 이전 폴백은 100 높이 안에 60짜리 셋을 넣어 33/34/33으로
찌그러뜨렸다. 유니티는 컨테이너가 180으로 자라고 자식이 60을 유지한 뒤 뷰포트가
잘라낸다. **좌표 몇 px이 아니라 자식 크기가 통째로 달라지는 문제였다.**

**알려진 차이: 스크롤바는 폭만 확보하고 그리지 않는다**(0.7.0까지, 2026-10-18 사람 결정 — 다음 버전 첫 후보).
스크롤바 내부 파트(7종)는 재현하지 않는다. 정지 화면 스코프 밖이고,
`golden.test.ts`의 `NOT_REPRODUCED`에 **명시적 목록**으로 두었다 — `unity-`
패턴으로 면제했다면 반드시 맞춰야 하는 `unity-content-viewport`까지 빠진다.

### 이 수치가 덮는 컨트롤

비교 대상 40개 케이스의 구성이다. 이전 측정(242/244)은 이 표의 첫 줄이 18개 중
17개였다 — 즉 **사실상 `VisualElement` 기하학**이었고, `Button`은 한 번도 대조된
적이 없었다.

**이 표는 `tests/golden/cases.ts`에서 계산한 것이며 기준은 이렇다**: `inventory`
케이스는 대표 화면으로 분류한다. 나머지 39개는 UXML에 `<ui:ScrollView`가 있으면
ScrollView, 없고 `<ui:Button`이 있으면 Button, 없고 `<ui:Label`이 있으면 Label,
셋 다 없으면 `VisualElement`만으로 분류한다 — `inventory`를 뺀 39개 전부 이
세 태그 중 최대 하나만 포함해서, 순서를 바꿔도 결과가 달라지지 않는다
(직접 확인함: 세 태그가 동시에 나오는 케이스는 `inventory` 하나뿐).

| 케이스 구성 | 개수 |
|---|---|
| `VisualElement`만 | 24 |
| `Label` 포함 | 1 (`inherit-vs-direct`) |
| `Button` 포함 | 10 |
| `ScrollView` 포함 | 4 |
| 대표 화면(인벤토리) | 1 — 위 5종 전부 + Image |

`Label`이 든 케이스가 하나뿐인 것은 나머지 둘(`text-size`·`text-align`)이
텍스트 측정에 의존해 비교에서 제외되기 때문이다. **컨트롤 커버리지는 값 개수와
다른 축이고, 값 개수가 늘어도 자동으로 늘지 않는다.**

`tests/golden/golden.test.ts`의 드리프트 가드가 이 표의 다섯 숫자도 같이
지킨다(2026-08-09부터) — 케이스가 늘 때마다 사람이 다시 세지 않아도 된다.

### 이 수치가 덮는 범위 — 중요

**이 97.9%는 Yoga가 계산한 좌표까지의 수치다.** 파이프라인은 네 층인데
(파싱 → 스타일 계산 → Yoga 레이아웃 → DOM 페인팅), 유니티와 대조하는 것은
세 번째 층의 출력이다. 화면에 실제로 그려진 DOM이 그 좌표를 재현하는지는
**유니티와 대조하지 않는다.**

빈 자리가 아니라 다른 방식으로 막는다. `tests/render/border-offset.test.ts`의
"CSS reproduces the Yoga geometry"가 페인팅된 트리를 거슬러 올라가며 각 요소의
패널 좌표를 CSS에서 역산하고, Yoga가 낸 값과 같은지 검사한다. 유니티가 아니라
**우리 자신의 두 층이 서로 맞는지**를 보는 검사다.

이 구분이 실제로 중요했다. 2026-08-03 코드 리뷰에서 **border가 있는 부모의 자손이
border 폭만큼 밀리는 버그**가 나왔는데, Yoga 좌표는 맞았고 CSS 변환이 틀렸다.
골든 테스트는 정의상 이걸 볼 수 없었고, 당시 렌더 테스트에는 border 있는 부모
케이스가 없었다. 위 불변식 검사가 그 구멍을 메운 것이다.

측정 환경:

| | |
|---|---|
| Unity | **6000.0.40f1** (Unity 6.0. 기준 버전 6.3 LTS의 재측정은 아래 절) |
| `yoga-layout` | 3.2.1 |
| 패널 크기 | 400 × 300 |
| 허용 오차 | 0.5px |
| 2026-08-12 덤프 DPI | `EditorGUIUtility.pixelsPerPoint = 1`, Windows `AppliedDPI = 96` |
| 2026-08-12 덤프 폰트 | Editor `(builtin)`, 12, Normal; font smoothing 2/type 2/gamma 0 |

> Unity 버전은 결과를 좌우한다. UI Toolkit이 벤더링한 Yoga가 버전마다 다르기
> 때문이고, 아래 불일치가 정확히 그 문제다. **다른 Unity 버전에서 재측정하면
> 이 표를 그 버전으로 새로 채운다.** 덮어쓰지 말고 버전별로 나란히 둔다.

## 왜 픽셀이 아니라 좌표인가

유니티는 자기 폰트 에셋으로, 브라우저는 `sans-serif`로 글자를 그린다.
안티앨리어싱과 서브픽셀 렌더링도 다르다. **레이아웃이 100% 정확해도 글자 픽셀은
전부 다르게 나온다.** 텍스트가 포함된 케이스에서 픽셀 diff를 재면 그 수치는
레이아웃 정확도가 아니라 폰트 차이를 재게 된다.

정말 답해야 하는 질문은 "내 레이아웃이 유니티와 같은 자리에 오나"이고,
그건 좌표로 답한다. 색·테두리·모서리 같은 시각 속성은 좌표가 말해주지 않으므로
별도로 눈으로 대조한다.

## 기준값 만드는 법

```
1. pnpm golden:emit
     tests/golden/cases.ts  ->  tests/golden/cases/*.uxml + *.uss

2. tests/golden/cases/ 폴더를 유니티 프로젝트로 복사 (예: Assets/GoldenCases/)
   tools/UxmlLayoutDump.cs 를 Assets/Editor/ 에 넣는다

3. 유니티: Tools > uxml-preview > Golden Case Dumper
   케이스 폴더 지정 -> Run -> 출력 폴더 지정

4. 나온 *.json 을 tests/golden/unity/ 로 복사

5. pnpm test:golden
```

기준값이 없는 케이스는 **실패가 아니라 건너뛴다.** 아무도 만들 수 없는 파일이
없다고 빌드가 깨지면 안 되고, 동시에 미측정이 통과로 보여서도 안 된다.

패널 크기는 각 JSON에 기록되고 웹 쪽이 그 크기로 다시 레이아웃한다.
두 곳의 숫자를 손으로 맞출 일이 없다.

## 판정 기준

- 요소별로 `x` / `y` / `width` / `height` 비교
- 허용 오차 **0.5px** — Yoga의 포인트 반올림에서 나오는 흔들림은 불일치가 아니다
- 조인 키는 UXML의 `name` 속성. 이름 없는 요소는 비교하지 않는다
- `measuresText: true` 케이스는 비교에서 제외한다. 브라우저가 Unity의 폰트 에셋으로 글자를 재지
  못하므로 여기서 나오는 차이는 레이아웃 오차가 아니다. 글자 상자 자체는 위 텍스트 코호트가
  실제 브라우저에서 따로 대조한다

## 고친 불일치 — 유니티의 컨트롤 기본 여백 (2026-08-05)

`Button` 케이스 5개를 처음 대조했더니 **48개 값 중 18개가 어긋났다.** 전부 같은
모양이었다 — x가 3px, y가 1px 밀리고, 행에서는 그 차이가 누적됐다.

원인은 레이아웃이 아니라 **빠진 입력**이었다. 유니티는 테마 스타일시트로 컨트롤에
기본 여백을 주는데 이 렌더러는 아무것도 주지 않았다. 가설을 세우고 계산으로
확인했다 — `.unity-button { margin: 1px 3px }` 한 줄을 넣으니 5개 케이스 48개 값이
**전부 일치**했다.

고친 방식이 중요하다. 좌표에 오프셋을 더한 것이 아니라 **유니티가 가진 것과 같은
스타일시트를 공급**했다. 전자는 CLAUDE.md 1번 규칙(레이아웃을 직접 구현하지 않는다)
위반이고, 후자는 입력을 맞추는 일이다. 값은 `src/controls/theme.ts`에 있다.

- 측정된 값만 넣는다. `Label`은 기본 여백이 **없다는 것이 측정 결과**다
  (`inherit-vs-direct`의 명시적 크기 Label이 유니티에서 x=0, y=0)
- padding·border·폰트는 **미측정**이라 넣지 않았다. 현재 케이스가 전부 명시적
  크기이고 USS가 border-box라 바깥 사각형을 움직이지 않으므로 보이지 않는다
- 셀렉터 `.unity-button`은 유니티의 문서화된 `Button.ussClassName`에서 왔고
  **처음에는 측정된 값이 아니었다.** 여백 덤프는 간격을 증명했지 그것을 전달하는
  셀렉터를 증명하지 않는다. 그래서 `theme-class-hook` 케이스를 만들어 판정을 맡겼고,
  **2026-08-05에 판정됐다** — author USS의 `.unity-button` 규칙이 맨몸 `<ui:Button>`에
  닿아 양쪽 모두 120×40이 나왔다. 이제 셀렉터도 측정된 값이다

**버전 의존이다.** 테마 값은 유니티 버전마다 다르므로, 적용될 때마다 측정 버전을
담은 `version-dependent` 경고가 문서당 한 번 나온다.

## 알려진 불일치 1건 — 크기 미지정 부모에 대한 `%`

**유니티가 옳고 우리가 틀렸다.**

```
부모: 크기 미지정, 자식: width 50% / height 50%, 패널 400 x 300

          유니티      우리
  부모     0 x 0      0 x 150
  자식     0 x 0      0 x 75
```

CLAUDE.md의 "`%` 크기는 부모에 명시적 크기가 없으면 계산되지 않는다"가 두 축 모두
맞다. `yoga-layout` 3.2.1은 **주축** 퍼센트를 크기가 확정되지 않은 부모에 대해서도
풀어버리고, UI Toolkit이 벤더링한 Yoga는 그러지 않는다.

| `Errata` 전 값 (`None` / `StretchFlexBasis` / `AbsolutePercentAgainstInnerSize` / `All` / `Classic`) | 변화 없음 |
| `ExperimentalFeature.WebFlexBasis` | 변화 없음 |
| `useWebDefaults(true)` | 축만 뒤바뀜 (200×0). **주축/교차축 문제이지 가로/세로 문제가 아님**을 확인 |
| 부모에 `flex-basis: 0` | **유니티와 같은 0×0.** 그러나 기본값으로 삼으면 명시적 높이를 가진 모든 요소가 0으로 붕괴 (`height: 40px` → `0`). 우연의 일치였고, 1개를 맞추려고 17개를 깨는 셈 |

설정으로 맞출 수 없고, 손으로 보정하려면 레이아웃 계산에 개입해야 한다.
**CLAUDE.md 1번 규칙(레이아웃을 직접 구현하지 않는다)이 금지하는 일**이고,
그 규칙이 있는 이유가 정확히 이런 보정이 시간이 지나며 어긋나기 때문이다.

그래서 `tests/golden/golden.test.ts`의 `KNOWN_DIVERGENCES`에 **정확히 두 값**으로
등록했다. 허용 오차를 늘리는 방식이 아니라 목록으로 두었기 때문에,
이 불일치가 사라지거나 번지면 테스트가 실패한다.

### 실무에서 의미

크기가 확정되지 않은 부모에 `%` 자식을 두는 것은 유니티에서 **어차피 동작하지 않는
패턴**이다. 우리 프리뷰는 그 상황에서 유니티보다 "관대하게" 그린다 —
유니티에서 안 보일 것이 프리뷰에서는 보일 수 있다. 반대 방향(프리뷰에서 안 보이는데
유니티에서 보임)은 아니므로, 프리뷰를 믿고 만든 UI가 유니티에서 깨지는 쪽은 아니다.
그래도 `%`를 쓸 때는 부모 크기를 명시하는 편이 안전하다.
