# Accuracy

*[English](accuracy.en.md) · 한국어*

**"유니티랑 진짜 똑같이 나오냐"에 숫자로 답하는 문서.**
공개했을 때 첫 번째로 받는 질문이고, 답이 없으면 아무도 쓰지 않는다.

## 현재 상태 (2026-08-02 측정)

| 항목 | 값 |
|---|---|
| 케이스 | 20 (비교 대상 18, 텍스트 측정 의존 2) |
| 유니티 기준값 확보 | **18 / 18** |
| 비교한 요소 | 61 (값 244개 = 요소 × x/y/width/height) |
| **케이스 일치** | **17 / 18** |
| **값 일치** | **242 / 244 (99.2%)** |
| 알려진 불일치 | 1케이스 2값 — 아래 |

허용 오차 0.5px. 불일치 2건은 모두 `percent-without-parent-size` 한 케이스에서
나왔고, 나머지 17개 케이스 59개 요소는 **오차 0으로 정확히 일치**한다.

### 이 수치가 덮는 범위 — 중요

**이 99.2%는 Yoga가 계산한 좌표까지의 수치다.** 파이프라인은 네 층인데
(파싱 → 스타일 계산 → Yoga 레이아웃 → DOM 페인팅), 유니티와 대조하는 것은
세 번째 층의 출력이다. 화면에 실제로 그려진 DOM이 그 좌표를 재현하는지는
**유니티와 대조하지 않는다.**

빈 자리가 아니라 다른 방식으로 막는다. `tests/render/border-offset.test.ts`의
"CSS reproduces the Yoga geometry"가 페인팅된 트리를 거슬러 올라가며 각 요소의
패널 좌표를 CSS에서 역산하고, Yoga가 낸 값과 같은지 검사한다. 유니티가 아니라
**우리 자신의 두 층이 서로 맞는지**를 보는 검사다.

이 구분이 실제로 중요했다. 2026-08-03 코드 리뷰에서 **border가 있는 부모의 자손이
border 폭만큼 밀리는 버그**가 나왔는데, Yoga 좌표는 맞았고 CSS 변환이 틀렸다.
골든 테스트는 정의상 이걸 볼 수 없었고, 당시 렌더 테스트에는 border 있는 부모
케이스가 없었다. 위 불변식 검사가 그 구멍을 메운 것이다.

측정 환경:

| | |
|---|---|
| Unity | **6000.0.40f1** (Unity 6) |
| `yoga-layout` | 3.2.1 |
| 패널 크기 | 400 × 300 |
| 허용 오차 | 0.5px |

> Unity 버전은 결과를 좌우한다. UI Toolkit이 벤더링한 Yoga가 버전마다 다르기
> 때문이고, 아래 불일치가 정확히 그 문제다. **다른 Unity 버전에서 재측정하면
> 이 표를 그 버전으로 새로 채운다.** 덮어쓰지 말고 버전별로 나란히 둔다.

## 왜 픽셀이 아니라 좌표인가

유니티는 자기 폰트 에셋으로, 브라우저는 `sans-serif`로 글자를 그린다.
안티앨리어싱과 서브픽셀 렌더링도 다르다. **레이아웃이 100% 정확해도 글자 픽셀은
전부 다르게 나온다.** 텍스트가 포함된 케이스에서 픽셀 diff를 재면 그 수치는
레이아웃 정확도가 아니라 폰트 차이를 재게 된다.

정말 답해야 하는 질문은 "내 레이아웃이 유니티와 같은 자리에 오나"이고,
그건 좌표로 답한다. 색·테두리·모서리 같은 시각 속성은 좌표가 말해주지 않으므로
별도로 눈으로 대조한다.

## 기준값 만드는 법

```
1. pnpm golden:emit
     tests/golden/cases.ts  ->  tests/golden/cases/*.uxml + *.uss

2. tests/golden/cases/ 폴더를 유니티 프로젝트로 복사 (예: Assets/GoldenCases/)
   tools/UxmlLayoutDump.cs 를 Assets/Editor/ 에 넣는다

3. 유니티: Tools > uxml-preview > Golden Case Dumper
   케이스 폴더 지정 -> Run -> 출력 폴더 지정

4. 나온 *.json 을 tests/golden/unity/ 로 복사

5. pnpm test:golden
```

기준값이 없는 케이스는 **실패가 아니라 건너뛴다.** 아무도 만들 수 없는 파일이
없다고 빌드가 깨지면 안 되고, 동시에 미측정이 통과로 보여서도 안 된다.

패널 크기는 각 JSON에 기록되고 웹 쪽이 그 크기로 다시 레이아웃한다.
두 곳의 숫자를 손으로 맞출 일이 없다.

## 판정 기준

- 요소별로 `x` / `y` / `width` / `height` 비교
- 허용 오차 **0.5px** — Yoga의 포인트 반올림에서 나오는 흔들림은 불일치가 아니다
- 조인 키는 UXML의 `name` 속성. 이름 없는 요소는 비교하지 않는다
- `measuresText: true` 케이스는 비교에서 제외한다. 유니티 폰트 메트릭과
  우리 측정식이 다르므로 여기서 나오는 차이는 레이아웃 오차가 아니다

## 판정된 가정

Phase 1~4에서 단정하지 않고 넘겼던 것들. 전부 이번 측정으로 확인됐다.

| 가정 | 어디서 왔나 | 판정 케이스 | 결과 |
|---|---|---|---|
| `flex-shrink` 기본값이 1 (Yoga 엔진값은 0) | `src/render/values.ts` | `flex-grow-shrink` | **맞음** |
| 우선순위를 트리플로 세고 pseudo-class를 class로 센다 | `src/style/specificity.ts` | `specificity-tie` | **맞음** |
| 요소를 직접 겨냥한 스타일이 상속을 항상 이긴다 | CLAUDE.md | `inherit-vs-direct` | **맞음** |
| 인라인이 모든 셀렉터를 이긴다 | CLAUDE.md | `inline-override` | **맞음** |
| `%`는 부모에 명시적 크기가 없으면 계산되지 않는다 | CLAUDE.md | `percent-without-parent-size` | **맞음 — 우리가 틀림** |
| 행 높이가 `font-size * 1.2` | `src/render/measure.ts` | `text-size` | 미판정 (텍스트 제외) |
| `-unity-text-align` 세로 정렬 매핑 | `src/render/css-map.ts` | `text-align` | 미판정 (텍스트 제외) |

`flex-shrink` 기본값 1은 특히 중요했다. Yoga 엔진 기본값은 0이라 그대로 뒀으면
줄어들어야 할 요소가 안 줄어들었을 텐데, **지원 속성을 전부 명시적으로 쓴다**는
Phase 4의 결정이 이걸 막았다.

## 알려진 불일치 1건 — 크기 미지정 부모에 대한 `%`

**유니티가 옳고 우리가 틀렸다.**

```
부모: 크기 미지정, 자식: width 50% / height 50%, 패널 400 x 300

          유니티      우리
  부모     0 x 0      0 x 150
  자식     0 x 0      0 x 75
```

CLAUDE.md의 "`%` 크기는 부모에 명시적 크기가 없으면 계산되지 않는다"가 두 축 모두
맞다. `yoga-layout` 3.2.1은 **주축** 퍼센트를 크기가 확정되지 않은 부모에 대해서도
풀어버리고, UI Toolkit이 벤더링한 Yoga는 그러지 않는다.

### 왜 안 고쳤나

맞출 방법을 찾다가 전부 실패했고, 그 과정을 남겨둔다.

| 시도 | 결과 |
|---|---|
| `calculateLayout`에 넘기는 가용 크기 변경 (undefined / NaN / auto) | 변화 없음 |
| `Errata` 전 값 (`None` / `StretchFlexBasis` / `AbsolutePercentAgainstInnerSize` / `All` / `Classic`) | 변화 없음 |
| `ExperimentalFeature.WebFlexBasis` | 변화 없음 |
| `useWebDefaults(true)` | 축만 뒤바뀜 (200×0). **주축/교차축 문제이지 가로/세로 문제가 아님**을 확인 |
| 부모에 `flex-basis: 0` | **유니티와 같은 0×0.** 그러나 기본값으로 삼으면 명시적 높이를 가진 모든 요소가 0으로 붕괴 (`height: 40px` → `0`). 우연의 일치였고, 1개를 맞추려고 17개를 깨는 셈 |

설정으로 맞출 수 없고, 손으로 보정하려면 레이아웃 계산에 개입해야 한다.
**CLAUDE.md 1번 규칙(레이아웃을 직접 구현하지 않는다)이 금지하는 일**이고,
그 규칙이 있는 이유가 정확히 이런 보정이 시간이 지나며 어긋나기 때문이다.

그래서 `tests/golden/golden.test.ts`의 `KNOWN_DIVERGENCES`에 **정확히 두 값**으로
등록했다. 허용 오차를 늘리는 방식이 아니라 목록으로 두었기 때문에,
이 불일치가 사라지거나 번지면 테스트가 실패한다.

### 실무에서 의미

크기가 확정되지 않은 부모에 `%` 자식을 두는 것은 유니티에서 **어차피 동작하지 않는
패턴**이다. 우리 프리뷰는 그 상황에서 유니티보다 "관대하게" 그린다 —
유니티에서 안 보일 것이 프리뷰에서는 보일 수 있다. 반대 방향(프리뷰에서 안 보이는데
유니티에서 보임)은 아니므로, 프리뷰를 믿고 만든 UI가 유니티에서 깨지는 쪽은 아니다.
그래도 `%`를 쓸 때는 부모 크기를 명시하는 편이 안전하다.
