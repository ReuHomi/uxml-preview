## 2. "컨트롤을 지원한다"의 판정 기준 (제안)

한 컨트롤이 아래를 **모두** 통과해야 `supported.md`와 정확도의 "컨트롤 범위"에 올린다. 일부만 통과하면 "부분"으로 적는다.

1. **기본 상자** — 그 컨트롤 probe의 모든 상태에서, 컨트롤과 **모든 파트**의 x·y·w·h가 두 테마의 6.3 덤프와 1px 이내.
   6000.0 덤프는 버전 차이로 분류(0.6.0 방식)
2. **구조와 클래스** — 미리보기가 만드는 파트 트리(타입·`name`·클래스)가 덤프와 같다. 작성자 셀렉터가 파트에 닿는지는
   `theme-class-hook`처럼 **Unity에서 잰 훅 케이스** 하나로 판정한다(예: `.unity-toggle__checkmark { width: 40px; }`가 Unity와 같이 커지는가)
3. **상태별 크기** — 체크됨·값(최소/중간/최대)·비활성·라벨 있음/없음·`text`·placeholder·여러 줄·세로 방향. probe에 든 상태 전부
4. **색** — 기본·비활성·올림·누름·포커스의 배경·테두리·글자색이 덤프의 resolved style과 같다. 이번 측정으로 색도 숫자로 잴 수 있다
5. **그린 모습** — 체크 표시·손잡이·막대 같은 그림은 사람이 Unity와 나란히 보고 확인한다(`docs/visual-check.md`, 테마별 스크린샷).
   측정으로 대신하지 않는다
6. **모자란 부분은 경고** — Unity 내장 그림을 똑같이 그리지 못하는 등 남는 차이는 경고 목록에 남는다(절대 규칙 6)
7. **왕복** — 컨트롤 속성(`value`, `label`, `text`, `low-value` …)이 parse → serialize에서 보존(지금도 통과, 회귀 테스트로 묶음)

정확도 표에는 "컨트롤 범위"를 따로 둔다(CLAUDE.md 검증 규율 4). 예: "컨트롤 15종 중 대조 완료 n종".

## 3. 테마 옵션의 공개 계약

```ts
render(doc, el, { theme: 'runtime' });   // 기본값
render(doc, el, { theme: 'editor' });    // Unity 에디터(어두운) 테마 — 0.6.0까지의 화면에 가까움
```

| 항목 | 제안 |
|---|---|
| 이름 | `RenderOptions.theme?: 'runtime' \| 'editor'` — 열린 집합(나중에 `'editor-light'` 등). 소비자는 모르는 값에 기본 분기 |
| 기본값 | `'runtime'` |
| 결과에 기록 | `RenderResult.theme` — 실제로 쓴 테마. 소비자가 화면에 표시하고, 스킬이 보고에 적는다 |
| 테마별 값의 출처 | `src/controls/theme.ts`를 테마별 시트 둘로. 값은 전부 `probe-panel`/`probe-editor-070` 덤프에서. `THEME_UNITY_VERSION`은 테마마다 |
| 정확도 | 좌표 정확도 660/676은 **에디터 테마·6000.0의 기존 세트**로 유지. 런타임은 새 세트(골든 44케이스 런타임 6.3 덤프)로 따로 낸다. 합산하지 않는다 |

**지금 쓰는 사람에게 보이는 변화** (기본값이 바뀔 때):
- 글자가 12px → 14px로 커지고, 글자색이 밝은 회색 → 거의 검정으로 바뀐다. 배경이 없는 화면은 어두운 글자가 된다
- Label마다 위아래 여백이 생겨 한 줄 Label이 15 → 25px, Button이 19 → 39px 높이가 된다. 글자가 든 화면은 전부 아래로 길어진다
- Unity 기준으로는 이게 맞는 화면이다(골든 11케이스·125값이 Unity에서도 그렇게 움직인다)

> 2026-10-17 사람의 결정: 기본값은 런타임. VSCode·스킬의 알림은 이 저장소의 범위가 아니다 — 아래 2·3번은 소비자 저장소의 몫으로 남기고, 코어는 1·4번만 한다.

**알리는 방법** (제안):
1. CHANGELOG 0.7.0 첫 항목 "기본 테마가 런타임으로 바뀜 — 예전 화면은 `theme: 'editor'`"
2. `RenderResult.theme`를 소비자가 표시: VSCode 미리보기 도구막대에 테마 선택(기본 Runtime), 스킬 보고 첫 줄에 "theme: runtime"
3. 0.7.0으로 처음 열었을 때 한 번 알리기는 **소비자 쪽** 일이다(VSCode: 한 번 뜨는 안내). 코어는 경고 목록에 넣지 않는다 —
   경고는 "Unity와 다르다"는 뜻이고 이건 Unity와 같아지는 변화이기 때문
4. README 네 언어의 정확도 줄에 "에디터 테마 기준"을 적고 런타임 수치를 새 줄로(README 수치 테스트가 둘 다 잡도록 규칙 확장)

## 6. 합격 화면 — 대표 설정 화면 (측정용 설계)

`tests/golden/cases.ts`에 `settings`로 넣는다. 원칙: **오차가 숨지 않게** — 높이는 내용이 정하게 두어 한 컨트롤의 오차가 아래로
밀려 드러나게 하고, 폭은 고정 열과 맞춰 줄이는 줄을 둘 다 둔다. 모든 요소에 `name`. 글자는 영문(기본 폰트, `font-fallback` 없음),
한국어판은 폰트를 지정한 두 번째 변형으로.

```
settings (800×600, 가로)
├─ left (width 380)
│  ├─ GroupBox "Graphics"
│  │   Toggle "Fullscreen" (value=true) · Toggle "VSync"
│  │   RadioButton ×3 "1280×720 / 1920×1080 / 2560×1440" (가운데 체크)
│  │   Slider "Brightness" 0–1, 0.7, show-input-field · SliderInt "FPS limit" 30–144, 60
│  └─ GroupBox "Audio"
│      Slider "Master" 0–100, 80 · Slider "Effects" 0–100, 0
│      Toggle "Mute" (value=true, enabled=false)
└─ right (flex-grow 1)
   ├─ Box "account"
   │   TextField "Name" value · TextField placeholder-text · TextField password
   │   TextElement 설명 한 줄 · ProgressBar "Download" 50
   ├─ Slider 세로 (height 120) — 폭 오차 확인용
   └─ footer (row, align-items: flex-start — 폭이 내용으로 정해짐)
       Button "Apply" · Button "Cancel" (enabled=false) · RepeatButton "−" · RepeatButton "+"
```

- 15종 전부(기존 5 + 범위 10)를 한 화면에 쓴다 — 컨트롤 범위를 "값 개수"가 아니라 "대조된 컨트롤"로 센다
- 두 테마·두 버전으로 덤프. 같은 화면에 `states`로 Apply 올림·누름, Name 포커스를 준 변형 하나 → 색 판정(기준 4)

## 8. "상태별 모습만" vs "직접 눌러 보기" — 공수 비교와 권고

| | 상태별 모습만 | 직접 눌러 보기 |
|---|---|---|
| UI Builder | — | **지원한다**(1-5) |
| 공통 작업 | 속성(`value`, 체크, 비활성)에서 정적인 그림 — **둘 다 필요** | 같음 |
| 추가로 필요한 것 | 기존 `states` 옵션으로 올림·누름·포커스 색 | 문서와 따로 사는 임시 상태 저장소, 누를 때마다 다시 배치·그리기, 끌기 → 값 → 손잡이 위치(공식 추가 측정), **글자 입력**(커서·선택·한글 조합 입력), 키보드 포커스 이동, 소비자마다 입력 이벤트 연결 |
| 받는 소비자 | 셋 다(VSCode·CLI·스킬) | VSCode만. CLI·스킬은 그림만 본다 |
| 예상 Codex 라운드 | 묶음 B–F 안에 포함 | +4~6 (TextField 입력만 3 이상) |
| 측정 근거 | 덤프로 잰다 | 상호작용 중 모습은 덤프로 못 잰다 — 사람 대조만 |

**권고: 0.7.0은 상태별 모습만.** UI Builder는 지원하지만, 사람의 기준 중 "구현 부담이 크다"에 해당한다 — 특히 글자 입력(한글 조합)과
끌기는 이 프로젝트의 측정 규율로 검증할 수단이 없다. 값이 저장되지 않는 UI Builder와 같은 동작이라면 사용자가 얻는 것은 "눌렀을 때
어떻게 보이나"인데, 그것은 `states`(올림·누름·포커스)와 속성 값으로 이미 보여 줄 수 있다. 나중에 한다면 Toggle·Radio 누르기와
올림·누름 따라가기처럼 싼 것부터(0.8 후보, backlog).

## 10. 위험과 미결 질문

### 위험
- **실제 게임의 PanelSettings는 다양하다.** 이번 측정은 배율 1·Text Settings 비움 기준이다. 많은 게임은 화면 크기에 맞춰 늘이는 배율을 쓰고,
  Text Settings 자산에 폰트·줄바꿈 규칙을 넣는다 → 크기·금칙이 달라질 수 있다 [추론]
- **Unity 내장 그림**(체크 표시 `check`·`d_toggle_on`, 손잡이)은 미리보기가 그대로 쓸 수 없다. 비슷하게 그린 그림은 측정이 아니라 사람 대조만 된다
- 기본값 변경은 **소비자의 모든 화면 스냅숏을 바꾼다**. 소비자 갱신을 묶음 A 바로 뒤에 두는 이유
- 슬라이더 손잡이 위치 공식은 값 3개만 쟀다. 묶음 D 전에 추가 측정 필요 — **2026-10-17 측정됨**(묶음 A 계획 20절: t × (끌기 칸 − 손잡이), 세로는 1 − t)
- 골든 기준값은 `UxmlLayoutDump`로, 런타임 세트는 `PanelDump`로 떴다. 두 덤퍼의 배치 차이를 세트 안에서 섞지 않는다
- 0.6.0 `probe-runtime` 덤프(테마 시트 교체 방식)는 실제 런타임 패널과 다를 수 있다 — 근거로 쓰지 않는다

### 알려진 근사 (2026-10-17 검토)
- **기본 텍스트 생성기를 테마 시트 값으로 표현한다.** 덤프의 `unityTextGenerator`는 런타임 패널(`probe-panel`) 두 버전 Standard,
  에디터 창(`probe-editor-070`) 6000.0 Standard·6.3 Advanced다. 그런데 6.3에서 에디터 시트를 런타임 패널에 얹어도(`golden-editor-on-panel`)
  Standard다 — 기본 생성기는 테마 시트가 아니라 **패널이 정하는 값**으로 보인다 [추론]. 미리보기는 이것을 런타임 시트의
  `-unity-text-generator: standard`(`src/controls/theme.ts`)와 에디터 테마의 advanced 기본값으로 표현한다. 결과(측정기에 넘기는 생성기)는
  같지만 출처가 다르다: 미리보기에서는 이 값이 `builtin-theme` 출처로 상속되어 작성자 규칙과 같은 캐스케이드를 탄다. Unity에서 테마 시트를
  바꿔도 생성기가 그대로인 경우(예: 자기 테마 파일을 쓰는 게임)를 미리보기는 구별하지 못한다
- 런타임 자간·어간 폭은 2026-10-17 측정(`r1-text-spacing`, 런타임 패널 두 버전)으로 standard 규칙과 1px 안에서 일치한다(`tests/contract-070/r1-measured.test.ts`)
