## 1. 목표와 성공 기준

**목표**: 인벤토리 화면 1개를 uxml-preview에서 확인하고, 같은 `.uxml`/`.uss`를 Unity에서 열었을 때 **동일한 구조와 좌표**로 나오는 것.

**성공 기준 (합격/불합격 판정 가능한 형태로)**

| # | 기준 | 판정 방법 |
|---|---|---|
| 1 | 대표 화면의 모든 노드가 화면에 나타난다 | cascade-hide로 사라진 노드 0개 |
| 2 | 노드 좌표가 Unity와 일치한다 | 각 노드 `x/y/width/height` 오차 ≤ 1px |
| 3 | 시각 속성이 Unity와 일치한다 | 요소별 CSS 선언 골든 스냅샷(자동 회귀) + 대표 화면 1회 육안 대조를 **산출물로 기록** — 스크린샷 2장을 `docs/media/`에 커밋하고 색·테두리·모서리 각각 체크 |
| 4 | 버튼이 죽어 보이지 않는다 | `:hover`/`:active`/`:disabled` 상태별 렌더 결과가 Unity와 일치 |
| 5 | 왕복 보존이 깨지지 않는다 | 기존 round-trip 바이트 일치 테스트 전부 통과 |

**성공 기준이 아닌 것**: 지원 컨트롤 개수, USS 속성 개수. 숫자는 목표가 아니라 부산물.

## 2. 대표 화면 정의 — 인벤토리

대표 화면이 컨트롤 목록을 결정한다. 반대 방향(컨트롤을 먼저 늘리고 화면을 맞추기)은 스코프 폭주의 시작점이므로 금지.

### 화면 구성

```
InventoryRoot (VisualElement)
├── Header (VisualElement)
│   ├── TitleLabel (Label)          "인벤토리"
│   └── CloseButton (Button)        "X"
├── ItemGrid (ScrollView)
│   └── ItemSlot × N (VisualElement)
│       ├── ItemIcon (Image)        에셋 경로 참조
│       ├── ItemCount (Label)       우하단 겹침 배치
│       └── (선택 상태: USS 클래스)
└── Footer (VisualElement)
    ├── DetailPanel (VisualElement)
    │   ├── ItemName (Label)
    │   └── ItemDesc (Label)         멀티라인 텍스트
    └── ActionBar (VisualElement)
        ├── UseButton (Button)       기본 상태
        └── DropButton (Button)      disabled 상태 포함
```

### 이 화면을 고른 이유

- **실무 대표성**: 게임 UI에서 가장 흔한 형태. 포럼에 올렸을 때 "내 화면이랑 비슷하다"는 반응이 나옴
- **필요 요소가 자연스럽게 다 들어감**: 스크롤되는 목록, 아이콘 이미지, 겹침 배치, 멀티라인 텍스트, 버튼 상태
- **겹침 배치가 들어감**: USS에는 `z-index`가 없고 형제 순서로 결정되므로, 수량 뱃지를 아이콘 위에 올리는 것만으로 이 규칙을 검증하게 됨
- **확장 유혹이 적음**: 입력 필드나 슬라이더를 억지로 넣을 이유가 없는 화면

## 3. 지원 범위

### 3.1 IN — 이번에 한다

**컨트롤**

| 컨트롤 | 상태 | 비고 |
|---|---|---|
| `VisualElement` | 기존 | — |
| `Label` | 기존 | 멀티라인/워드랩 검증 추가 |
| `Button` | 기존 | 골든 테스트 0개 → 상태별 케이스 추가 |
| `Image` | **신규** | `resolveAsset` 훅 경유 |
| `ScrollView` | **신규(최소)** | 정지 렌더만, 아래 3.3 참고 |
| 그 외 전부 | **신규 폴백** | `VisualElement`로 렌더 |

**pseudo-class 상태 해석 (일부 기구현)**
- `:hover` / `:active` / `:disabled` / `:checked` 의 **스타일 해석** — 매칭 경로는 이미 있다
  (`RenderOptions.activeStates` → `ResolveOptions` → `MatchContext` → `matchesSimple`)
- 상태는 **명시적 입력**으로 받는다 (마우스 이벤트 아님) — 결정적 렌더링 유지
- API 형태: `render(doc, container, { states: { "#UseButton": ["hover"] } })`
  — 현행 `activeStates`(문서 전역 `Set`)는 **요소별 맵으로 확장한다.** 대표 화면에
  기본 버튼과 disabled 버튼이 동시에 있어서 전역 집합으로는 그 화면을 그릴 수 없다.
  키의 셀렉터 문법은 기존 셀렉터 파서를 재사용하고, 전역 `activeStates`는 하위 호환으로 남긴다
- `:disabled`가 Unity에서 `SetEnabled`로 하위 트리에 상속되는 것은 **이번 범위 밖**이다

**USS 속성** — 대표 화면에 필요한 것만
- flex: `flex-direction`, `flex-grow`, `flex-shrink`, `flex-basis`, `justify-content`, `align-items`, `align-self`, `flex-wrap`
- 크기: `width`, `height`, `min-*`, `max-*`, `margin`, `padding`
- 위치: `position`, `top`/`right`/`bottom`/`left`
- 색: `background-color`, `color`
- 테두리: `border-*-width`, `border-*-color`, `border-*-radius`
- 이미지: `background-image`, `-unity-background-scale-mode`, `-unity-background-image-tint-color`
- 텍스트: `font-size`, `-unity-font-style`, `-unity-text-align`, `white-space`, `text-overflow`
- 기타: `opacity`, `display`, `visibility`, `overflow`

> 이 목록에서 **미구현은 `-unity-background-scale-mode` 하나뿐이다.** 나머지는 착수
> 시점에 `src/render/css-map.ts`와 `src/layout/yoga.ts`에 이미 있다.

**테스트**
- Button 골든 케이스 (상태 4종 × 최소 1케이스)
- 시각 속성 대조 — 요소별 **CSS 선언 골든 스냅샷**. 자동 픽셀 diff는 하지 않는다
  (기준 3 참조). `pixelmatch`/`pngjs`는 devDep에 남지만 이번에 쓰지 않는다
- 대표 화면 전체 골든 케이스 1개
- 신규 컨트롤당 골든 케이스 최소 1개

### 3.2 OUT — 명시적으로 안 한다

새 항목을 넣고 싶어질 때마다 이 목록을 먼저 볼 것.

| 항목 | 안 하는 이유 |
|---|---|
| **버튼 내비게이션 / 클릭 동작** | UXML에 이벤트 바인딩 문법이 없음. 전적으로 C# 영역이라 브라우저에서 재현할 대상 자체가 없음 |
| **실제 스크롤 상호작용** | 정지 화면 검증이 목적. 스크롤 위치는 골든 테스트의 결정성을 깨뜨림 |
| **마우스 이벤트 기반 상태 전환** | 상태는 명시적 입력으로만. 실제 hover 구현은 S1.5(VSCode 뷰어)에서 편의 기능으로 검토 |

| UI Builder류 편집 기능 | 프로젝트가 명시한 "하지 않을 일" |

### 3.3 ScrollView를 "최소"로 한다는 것의 정확한 의미

ScrollView는 단순한 박스가 아니다. Unity에서 ScrollView는 **암묵적 자식 계층**을 갖고, 이 계층이 레이아웃 좌표에 직접 영향을 준다.

> **아래 2계층 그림은 틀렸다.** 착수 시점의 추정이었고, 2026-08-05 유니티 덤프가
> 반증했다. 실측 구조는 이 절 끝의 "실측 결과"에 있다 — 계층은 **셋**이다.
> 원문을 남겨두는 이유는 이 오해가 어디서 왔는지 보이기 위해서다.

```
ScrollView
└── #unity-content-viewport      ← 클리핑 담당, overflow: hidden
    └── #unity-content-container ← 실제 자식들이 여기 들어감
```

즉 `<ui:ScrollView><ui:Button/></ui:ScrollView>` 라고 써도, Button의 부모는 ScrollView가 아니라 content-container다. 이 계층을 재현하지 않으면 **좌표가 어긋난다** — 이게 "박스 하나로 대충 그리면 안 되는" 이유.

### 실측 결과 (Unity 6000.0.40f1, 2026-08-05)

```
ScrollView
└── #unity-content-and-vertical-scroll-container   ← 추정에 없던 층
    └── #unity-content-viewport                    ← 클리핑
        └── #unity-content-container               ← 사용자 자식이 여기
```

그 밖에 **이름 없는 Scroller 둘**(가로·세로)이 있고, 그 안의 파트만 이름을 갖는다
(`unity-dragger` 등 7종 × 2). 스크롤러 자체는 이름이 없어 덤프에 안 나온다.

**측정된 규칙**

| | 관측 | 규칙 |
|---|---|---|
| 1층 | padding 15+border 5인 200×120에서 `20,20` / `160×80` | ScrollView의 **content box를 채운다** |
| 2층 뷰포트 | 넘칠 때 `187×100`, 안 넘칠 때 `200×120` | 세로 스크롤바가 **13px**를 가져간다. 안 넘치면 스크롤바가 `0×0`이라 폭이 온전하다 |
| 3층 컨테이너 | 콘텐츠 40일 때 높이 `40`, 콘텐츠 180일 때 높이 `180` (뷰포트는 100) | 높이가 **콘텐츠 높이**다. 뷰포트에 맞춰 줄지 않는다 — **자식이 압축되지 않는 이유** |
| 자식 | 폭 미지정이면 `187` | 컨테이너 폭으로 stretch (column 방향의 교차축) |

**3층의 높이가 이번 구현의 핵심이다.** 지금 폴백은 높이 100 박스 안에 60짜리 셋을
넣어 `flex-shrink`로 33/34/33으로 찌그러뜨린다. 유니티는 컨테이너가 180으로 자라고
자식이 60을 유지한 뒤 **뷰포트가 잘라낸다.**

**하는 것**: 위 암묵 계층 생성, 뷰포트 클리핑, 콘텐츠가 넘칠 때의 레이아웃 계산
**안 하는 것**: 스크롤바 드래그, 휠 이벤트, 스크롤 위치 상태, 스크롤바 자동 표시/숨김 로직(초기 상태만 재현)

같은 주의사항이 `Button`에도 적용된다. Unity의 Button은 `TextElement` 계열이라 **텍스트를 자기 자신이 직접 렌더**하며, 내부에 Label 자식을 만들지 않는다. 웹 감각으로 `<button><span>` 구조를 만들면 좌표가 틀어진다.

## 4. 작업 순서

각 단계는 앞 단계가 끝나야 시작한다. 순서가 뒤집히면 검증 없이 기능을 쌓게 된다.

### Step 1 — 폴백 렌더링 (가장 먼저) — **완료 (2026-08-05, `cb4f9f0`)**
미지원 컨트롤을 `VisualElement`처럼 그려서 cascade-hide 해소.

- 렌더러 조회 실패 시 폴백 경로로 진입
- 폴백은 **기본 경로**, 전용 렌더러가 예외 — 조건문 방향을 이렇게 잡아야 새 컨트롤이 추가돼도 안전
- 폴백 적용 시 경고 1건 발생 (에러 아님)
- 이 단계만으로 체감 개선이 가장 큼

#### 구조를 어디서 알아낼 것인가 — 확인 결과 (2026-08-05)

후보는 셋이었다 — GitHub `needle-mirror` 소스(A), 로컬 유니티 설치(B),
덤프로 역산(C). C를 골랐고, 가는 길에 **틀린 확인을 한 번 했다.**

**틀렸던 확인**: 하네스의 `Collect`가 `element.Children()`을 순회하므로
"실제 비주얼 트리를 따라간다"고 판단했다. 코드만 보면 그럴듯하다.
**실측이 반증했다** — `scrollview-hierarchy`가 2개 요소만 찍혔다.
`sv-plain`과 `sv-plain-child`뿐, 암묵 파트는 없었다.

**원인**: `Children()`은 트리가 아니라 그 요소의 **`contentContainer`**를 순회한다.
`ScrollView`는 `contentContainer`를 `#unity-content-container`로 덮어쓰므로,
ScrollView에게 자식을 물으면 **중간 두 계층을 건너뛰고** 사용자 요소를 돌려준다.
물리 트리는 `element.hierarchy`이고, 그쪽에는 이 우회가 없다. 그렇게 고쳤다.

**이 사건이 규율의 근거를 하나 더 준다.** 나의 "확인"도 결국 소스 읽기였고,
소스 읽기는 판정 전까지 가설이다 — `.unity-button` 클래스명 때와 같은 종류다.
차이는 이번엔 케이스가 이미 있어서 **한 번의 덤프가 즉시 반증했다**는 것뿐이다.
케이스를 구현보다 먼저 쓰지 않았다면, 이 오류는 ScrollView 구현이 끝난 뒤에
"좌표가 왜 안 맞지"로 나타났을 것이다.

**함정 하나를 미리 막았다.** 덤프는 이름을 키로 하는 JSON 객체인데, 암묵 파트는
모든 `ScrollView`에서 이름이 같다. 한 케이스에 `ScrollView`가 둘이면
`unity-content-container`가 **조용히 덮인다.** 덤퍼에 중복 이름 감지를 넣었고,
케이스는 하나씩만 두도록 썼다.

#### 1차 덤프에서 이미 얻은 것 (암묵 파트가 빠졌어도)

계층은 못 봤지만 **바깥에서 관측되는 사실 셋**은 나왔다. 전부 실측이다.

| 케이스 | 관측 | 의미 |
|---|---|---|
| `scrollview-overflowing` | 200 폭 ScrollView 안에서 자식이 **187** | 세로 스크롤바가 **13px**를 가져간다 |
| `scrollview-overflowing` | 자식이 `x: 0`, `y: 0 / 60 / 120` | 패딩이 없으면 뷰포트·컨테이너가 **오프셋을 더하지 않는다**. 넘치는 콘텐츠도 잘리지 않고 그대로 쌓인다 |
| `scrollview-padding` | 자식이 `x: 20, y: 20` (padding 15 + border 5) | padding·border는 **ScrollView 자신**에 적용되고, 콘텐츠는 그 안쪽에서 시작한다. 계층이 추가 오프셋을 만들지 않는다 |

**이 값들은 기준값으로 설치하지 않았다.** 암묵 파트가 빠진 불완전한 덤프이고,
설치하면 그 2~4개 이름만 비교하면서 통과해버린다 — 계층이 검증되지 않았는데
"측정됨"으로 읽히는 상태다. 확보율을 24/27로 유지하는 편이 정직하다.

(같은 덤프에서 기존 27개는 **또 바이트 일치**했다. 세 번째다.)

#### 구현 전에 알아야 할 결과 하나

우리 쪽 `runCase`는 **모델 트리**를 순회하며 `name` 속성을 키로 쓴다. 암묵 자식은
모델에 없고 `name` 속성도 없다 — 모델에는 파일에서 온 것만 넣는다는 원칙 때문이다.

즉 계층을 구현해도 **암묵 노드가 우리 출력에 나타나지 않으면 대조 자체가 불가능하다.**
레이아웃 트리가 합성 노드를 이름과 함께 내보내는 경로가 필요하고, 그건 구현의
부수 작업이 아니라 **전제**다. 지금 적어두는 이유는 구현 도중에 발견하면
설계를 되돌려야 하기 때문이다.

1. **파서 동작과 UXML 보존 로직은 변경하지 않는다.** UXML 전체 보존은 이미 달성됐고, 이번 작업은 렌더러 계층에 한정. 파서 수정이 필요해 보이면 그건 별도 이슈다.
   `src/model/types.ts`의 **타입 확장은 파서 동작을 바꾸지 않는 한 허용**하되, 왕복 테스트 전체 통과를 확인하고 보고한다. 경계는 파일이 아니라 동작이다 — 자세한 이유는 `CLAUDE.md`의 "변경 범위" 절 (2026-08-05 개정)
2. **컨트롤 하나 = 파일 하나 + 골든 테스트 하나.** 테스트 없는 컨트롤은 머지하지 않는다
3. **폴백이 기본, 전용 렌더러가 예외.** 새 컨트롤 추가가 기존 동작을 깨뜨릴 수 없는 구조
4. **미지원은 경고, 에러 아님.** 기존 원칙 유지. 렌더링은 항상 최선을 다해 진행된다
5. **결정적 렌더링.** 시간·난수·실제 입력에 의존하는 코드를 렌더 경로에 넣지 않는다. 상태는 전부 명시적 파라미터
6. **provenance 유지.** 새 렌더러도 "이 DOM 노드가 어느 UXML 노드/USS 규칙에서 왔는지"를 반드시 기록. S3에서 이게 없으면 편집이 불가능해진다
7. **좌표는 Yoga가 정한다.** 렌더러가 위치를 보정하지 않는다. 안 맞으면 트리 구조가 틀린 것이지 보정할 문제가 아니다

## 6. 철학

> **먼저 안 깨지게, 그 다음에 정확하게, 마지막에 많이.**

Step 1(폴백=안 깨짐) → Step 2~3(골든=정확) → Step 4~5(컨트롤=많이) 순서가 이 문장 그대로다.

컨트롤 개수는 신뢰의 결과지 원인이 아니다. 3종만 지원해도 그 3종이 Unity와 픽셀 단위로 맞으면 신뢰를 얻지만, 10종을 지원해도 좌표가 틀리면 아무도 안 쓴다.

> **하위 트리를 죽이지 않는다.**

미지원 컨트롤 하나 때문에 그 아래 전부가 사라지는 건 "지원 안 함"이 아니라 "고장"이다. 폴백을 최우선에 두는 이유.

## 7. 참고 레포

### `needle-mirror/com.unity.ui` — 필수
https://github.com/needle-mirror/com.unity.ui

UI Toolkit 소스 미러(UPM 미러, Unity Technologies 비공식). **정답지 역할.**

**볼 곳**
- `ScrollView` 구현 — `#unity-content-viewport` / `#unity-content-container` 계층 구성과 각각에 적용되는 기본 스타일. Step 5의 좌표 일치는 이 구조를 정확히 베끼는 데 달려 있다
- `Button` 구현 — `TextElement` 상속 구조 확인. 텍스트를 자식 없이 직접 렌더한다는 사실의 근거
- 기본 테마 USS — 각 컨트롤의 기본 `padding`/`margin`/`border`. 이 값을 모르면 "Unity에선 여백이 있는데 프리뷰엔 없다"가 반복된다
- `Image` 구현 — `scale-mode` 처리 방식

**주의**: 그대로 포팅하지 말 것. 이건 C# 구현이고 uxml-preview는 다른 언어·다른 렌더 타깃이다. **구조와 기본값만** 참고한다.

### `hackerzhuli/unity-code` (Unity Code Pro) — 권장
https://github.com/hackerzhuli/unity-code

USS를 100% 네이티브로 검증하는 VSCode 확장. 모든 USS 속성과 값을 검증하고 Unity와 거의 같은 에러를 낸다. `var()`가 들어간 값까지 검증을 시도한다.

**볼 곳**
- **USS 속성 목록과 각 속성의 허용 값 집합** — 3.1의 "지원 USS 속성" 목록이 빠뜨린 게 없는지 대조용. 특히 `-unity-` 접두 속성들
- 값 파싱 엣지 케이스 — 색상 표기, 길이 단위, 키워드 처리

**S1.5 관점의 의미**: 이 확장이 이미 USS IntelliSense·검증·hover 문서 영역을 차지했다. VSCode 뷰어를 만들 때 **이 영역은 침범하지 않는다**는 경계선으로도 쓴다. 미리보기는 비어 있는 자리다.

**주의**: Windows x64만 공식 지원하고 Dot Rush(C# language server)에 의존한다. 아키텍처를 따라할 대상은 아니고, 데이터(속성표)만 본다.

### `github.com/topics/uitoolkit` — 테스트 데이터 확보용
https://github.com/topics/uitoolkit

실제 배포된 UI Toolkit 프로젝트 모음. 토큰 + 24개 컴포넌트 + 63개 아이콘을 갖춘 디자인 시스템처럼 실전 투입된 UXML/USS 자산이 있다.

**볼 곳**
- **남이 쓴 진짜 `.uxml` 파일** — 대표 화면을 자기 손으로만 만들면 자기 구현에 맞는 파일만 만들게 된다. 외부 파일을 폴백 렌더링에 통과시켜보면 실제 구멍이 드러난다
- 실무에서 실제로 쓰이는 컨트롤 빈도 — S2 이후 컨트롤 우선순위의 근거

### Unity 공식 매뉴얼 — 명세 확인용
https://docs.unity3d.com/6000.3/Documentation/Manual/ui-systems/introduction-ui-toolkit.html

## 8. 다음 단계로 넘어가는 조건

S1 완료 = 성공 기준 5개 전부 통과 + 대표 화면 골든 테스트가 CI에서 돈다.

이 시점에 열리는 것:
- **S1.5 (VSCode 뷰어)** — 폴백이 있어야 남의 파일이 휑하지 않다. S1 완료가 전제 조건
- **홍보** — 대표 화면 스크린샷 2장(프리뷰/Unity) 나란히 놓는 게 가장 강한 증거물
- **S2** — 렌더 계층이 안정돼야 헤드리스 계층을 그 위에 올릴 수 있다

숫자를 인용할 때는 한정어를 같이 옮긴다. "242/244"는 **Yoga 레이어 기준**이며, 시각 속성 대조(Step 2)가 끝나기 전에는 이 숫자를 시각 정확도로 확장 해석하지 않는다.

**대외 숫자는 `242/244`(99.2%) 하나로 통일한다.** 세 숫자가 돌아다니는데 뜻이 다르다:

| 숫자 | 뜻 | 용도 |
|---|---|---|
| **242/244 (99.2%)** | 비교 값(요소 61개 × `x`/`y`/`w`/`h`) 중 일치한 수 | **대외 유일 숫자.** README·npm·사이트가 이미 이걸 쓴다 |
| 17/18 | 완전히 일치한 케이스 수 | 내부. 인용하려면 242/244와 함께 |
| 18/18 | 유니티 기준값을 확보한 케이스 수 | **정확도가 아니라 확보율.** 대외에 쓰지 않는다 |

18/18을 정확도로 잘못 인용한 적이 있어서 적어둔다. 골든 테스트가 찍는 문구도
`COVERAGE (not accuracy)`로 고쳤다. 포럼 글과 README가 다른 숫자를 말하면 그 자체가
신뢰 문제가 되므로, 새 숫자가 필요해지면 여기 표를 먼저 고친다.
